## 2. 개념

### 2.1 세 가지 사용 장면

1. **전시** — 글의 첫 장면. 사람 도슨트는 부담스럽고 오디오/텍스트 해설은 어렵다. 가장 친한 AI가 내 말투와 관심사로 설명해준다. 마지막에 AI가 감상을 정리해주고 관객이 직접 눌러 작가에게 보낸다(그래야 진짜 양방향).
2. **가게** — 고정 정보(메뉴, 화장실)는 지도 앱과 경쟁해서 약하다. 강점은 **오늘의 정보**(입고, 품절, 주인장 추천). 그러려면 주인이 자기 AI에게 말로 갱신하는 저작 흐름이 필요하다. 다국어는 덤(손님 AI가 번역).
3. **프로젝트 소개** — 가장 강하고 가장 먼저 만들 곳. "AI에게 검색시키면 아무거나 주워온다"는 문제를 주인이 큐레이션한 읽기 경로로 해결. 물리 안내판 없이 링크 하나로 됨. Patternflow 커뮤니티라는 실제 독자가 있음.

글의 순서는 전시 → 가게 → 프로젝트, **만드는 순서는 프로젝트(Patternflow) → 바 → 전시**.

### 2.2 두 개의 층

- **읽기 층**: 정적 페이지. 비용 0. 오늘 모든 AI에서 작동. Ganpan v0.1의 범위.
- **행동 층**: 후기, 주문, 예약 등. 지금은 "AI가 쓰고 사람이 보낸다"(AI가 내용을 정리 → 사람이 링크/버튼을 직접 누름). 표준 경로(MCP, WebMCP)가 이 시나리오에 닿으면 그쪽으로 옮긴다.

### 2.3 왜 지시가 아니라 서술인가

보안은 계속 조여지고 있고, 막히는 건 정확히 "페이지가 AI에게 시키는 문장"이다.
사용자가 직접 읽으라고 한 페이지를 읽고 그 내용으로 답하는 건 AI의 정상 기능이라 막히지 않는다.
따라서 페르소나·행동 지시 대신 **서술형 어포던스**를 쓴다:
섹션 구성, 상세 위치, 자주 묻는 질문, 관심사별 추천 동선 같은 "데이터".
AI는 이걸 데이터로 받고도 결과적으로 되묻고, 링크를 따라가고, 맞춤 설명을 한다.

### 2.4 포지셔닝

- 빅테크 표준이 덮는 곳: 브라우저 에이전트 + 열린 탭(WebMCP), 미리 연결한 서비스(MCP).
- **Ganpan의 자리**: 길 가다 들어온 손님 · 사전 설정 없음 · 폰 채팅 앱. 읽기는 되는데 행동의 표준 경로는 아직 없는 칸.
- 논거는 "챗봇이 단순해서"가 아니라 **"처음 온 손님의 AI는 여기가 뭔지 모른다"**는 상황에 둔다. AI가 발전할수록 간판에 적을 게 늘어난다.
- 진짜 경쟁자는 **지도/플레이스 데이터**(GPS 기반 조회). Ganpan의 차별점은 (a) 해상도: 가게가 아니라 작품·사물·오늘 단위, (b) 주인의 목소리: 플랫폼이 가공하지 않은 1차 정보.
- GEO 대행(이미 존재)은 "AI에게 발견·추천받기"를 최적화한다. Ganpan은 "손님이 일부러 AI를 들이댄 뒤의 대화"를 설계한다. 발견 vs 응대.
- 대기업은 통제와 데이터 때문에 자체 AI를 계속 만들 것. Ganpan의 시장은 자체 AI를 만들 여력이 없는 곳: 작은 가게, 작은 전시, 1인 메이커.

## 3. 조사 결과 (2026-09-20 웹 검색 기준)

### 3.1 용어와 선행 사례

- **"BYOA(Bring Your Own Agent)"는 이미 일반 용어.** 개발 툴(에이전트 구독을 오케스트레이션 플랫폼에서 사용), Microsoft 생태계, Red Hat, Everest Group 등 엔터프라이즈 맥락에서 널리 쓰임. Val Town 블로그는 새 용어가 아니라고 명시. BYOD에 빗댄 오래된 LinkedIn 글도 있음. → 이름으로 쓰지 않음.
  - https://www.augmentcode.com/guides/what-is-byoa-bring-your-own-agent
  - https://blog.val.town/byoa
  - https://centricconsulting.com/blog/12-ways-to-bring-your-own-agents-byoa-to-microsoft-ai/
- **미술관 AI 가이드 사례는 전부 "기관이 AI를 만들어 제공"하는 모델.** IBM×PalaisPopulaire의 MIA(자체 앱 내), PuppetGuide(콜로라도대), musa.guide 등. 관객이 혼자 ChatGPT를 도슨트처럼 쓴 후기(2025)와, 익숙한 채팅 인터페이스의 장점을 확인한 ACM IMX 2025 논문은 있음.
  - https://www.ibm.com/case-studies/palaispopulaire
  - https://dl.acm.org/doi/10.1145/3706370.3731650
  - https://medium.com/@groenestijnamber/use-chatgpt-as-your-personal-museum-guide-5955472552c7
- **"기관은 페이지만 내고 관객이 자기 AI를 데려온다"는 조합의 직접 선행 사례는 찾지 못함.** 단, 영어 위주 검색 몇 회의 결과이며 "없다"의 증명은 아님.

### 3.2 에이전트 웹 동향

- **llms.txt** (Jeremy Howard, 2024): 사이트 루트의 마크다운 안내 파일. 개발 문서 중심, 수동적 발견. 생성기·검증기까지 나와 있는 붐비는 영역. Google은 순위 신호로 쓰지 않는다고 밝힘. https://llmstxt.org
- **NLWeb** (Microsoft, 2025-05): 사이트를 자연어 질의 가능하게 하고 MCP 서버로도 동작.
- **MCP**: AI가 외부 서비스 도구를 호출하는 공개 규약. 서버 기반, 사용자가 미리 연결해야 함 → 제로 온보딩과 충돌.
- **WebMCP**: 웹페이지가 JS로 도구를 등록, 브라우저 내 에이전트가 호출. W3C **커뮤니티 그룹 초안**(2026-02-10), 정식 표준 트랙 아님. Chrome 149부터 origin trial, Chromium 전용, API가 이미 두 번 바뀜. **탭이 열려 있을 때만 작동** → 폰 채팅 앱 시나리오에는 직접 닿지 않음. 도구 발견(discovery)은 미해결 과제.
  - https://developer.chrome.com/docs/ai/webmcp/imperative-api
  - https://contextbolt.com/blog/what-is-webmcp/
- **간접 프롬프트 인젝션이 실전화.** Google은 크롤 데이터에서 악성 인젝션이 2025-11~2026-02 사이 32% 증가했다고 보고, Forcepoint는 실제 사이트에 심어진 페이로드를 확인. AI 회사들은 "가져온 콘텐츠 속 지시는 따르지 않는다" 방향으로 강화 중.
  - https://www.helpnetsecurity.com/2026/04/24/indirect-prompt-injection-in-the-wild/

### 3.2b 형식 재검토 (2026-09-20 두 번째 검색)

질문: "정적 HTML + 입구/조각"이 간판에 가장 맞는 형태인가, 더 나은 신기술이 있는가.

- **기본 형태를 대체할 것은 찾지 못함.** WebMCP·NLWeb·agents.json·A2A agent card·Agent Skills 등은 전부 미리 연결된 에이전트, 브라우저 안 에이전트, 또는 주인 쪽 서버를 전제한다. "길에서 들어온 손님 · 폰 채팅 앱"에 닿는 것은 여전히 "사용자가 건넨 URL을 읽는다"뿐.
- **llms.txt는 사실상 읽히지 않는다.** 한 집계에서 AI 봇 방문 5억 건 중 llms.txt를 직접 찾은 것은 408건. Google은 지원 계획 없음을 공언. → "발견을 기다리는 파일"이 아니라 "손님이 직접 건네는 주소"라는 Ganpan의 전제를 뒷받침.
  - https://limy.ai/blog/llms-txt-in-2026-the-full-guide
- **마크다운 콘텐츠 협상은 채택할 가치가 있음.** Cloudflare "Markdown for Agents"(2026-02): `Accept: text/markdown` 요청에 마크다운을 돌려줌. 한 사이트의 44일 로그에서 Anthropic 인프라(ClaudeBot 아님)가 500회 이 헤더를 보냄. ChatGPT·Gemini에 대한 데이터는 없음. → 원본이 마크다운이므로 `.md` 사본을 같이 내고 `<link rel="alternate">` 로 알리는 것으로 채택(SPEC 5.4). 열린 질문 "HTML vs 마크다운 병행"은 이것으로 닫음.
  - https://developers.cloudflare.com/fundamentals/reference/markdown-for-agents
  - https://suganthan.com/blog/cloudflare-markdown-for-agents/
- **호스팅이 손님의 AI를 막을 수 있다 (중요).** Cloudflare는 2026-07-01 AI 트래픽을 Search / Agent / Training 셋으로 나눠 관리하게 했고, Agent에 ChatGPT-User·Claude-User 같은 사용자 대행 fetcher가 들어간다. 2026-09-15부터 신규 도메인과 무료 플랜에서 Training·Agent가 기본 차단. 공식 글은 "광고가 있는 페이지에 한해"라고 하나, 2차 자료들은 범위를 더 넓게 적고 있어 **실제 동작은 직접 확인 필요**. 2025-07 이후 신규 zone의 "Block AI bots" 관리 규칙도 별개로 존재. 차단은 엣지에서 일어나 robots.txt로 풀 수 없음. → SPEC 6.5, 그리고 작은 가게가 간판을 달 때 가장 먼저 걸릴 함정.
  - https://blog.cloudflare.com/content-independence-day-ai-options/
  - https://dev.to/babel42/cloudflare-blocks-ai-agent-traffic-by-default-from-15-september-348g
- **Content Signals** (robots.txt의 `search` / `ai-input` / `ai-train`): IETF 초안은 만료, 지킬 의무 없음. 서술형 선언이라 원칙과 맞고 해가 없어 `ai-input=yes` 만 적어 둠. `ai-train` 은 작성자가 정할 일이라 비워 둠.
  - https://contentsignals.org/
- 선행 사례: 이번 검색에서도 "장소가 페이지만 내고 손님이 자기 AI를 데려오는" 배치 사례는 찾지 못함. 미술관 쪽은 여전히 기관 제공형.
- **언어 결정:** 규약과 ganpan.org의 간판은 영어를 정본으로, 규약은 한국어판 병기(`/ko`). 간판은 한 언어로만 쓴다 — "번역은 손님의 AI가 한다"가 이 프로젝트의 주장이므로 간판을 두 벌 만들면 그 주장을 스스로 깎는다. 가게·전시의 간판은 주인의 언어로 쓴다.

### 3.2c AI 앱은 어떤 주소를 여는가 (2026-09-20 세 번째 검색)

표준이 아니라 손님 쪽에서 실제로 일어나는 일을 봤다. 간판의 성패가 여기 달려 있다.

- **Claude (공식 문서):** 웹 fetch는 대화에 이미 등장한 URL만 연다. 사용자 메시지 속 URL, 검색 결과, 이전 fetch 결과에 나온 URL. **Claude 자신의 출력에만 등장한 URL은 거부**(`url_not_in_prior_context`). robots.txt가 막은 주소도 거부(`url_not_allowed`). JS 렌더링 미지원을 문서에 명시. 결과는 캐시됨. URL 최대 250자. API 문서 기준이며 소비자 앱이 같은지는 미확인.
  - https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool
- **ChatGPT (OpenAI, 2026-01-29 발표):** 에이전트는 독립 크롤러의 공개 웹 색인에 이미 있는 URL만 자동으로 연다. 그 밖은 "확인되지 않은 링크이며 대화 내용이 포함될 수 있다"는 경고를 띄우고 사용자가 고르게 한다. 목적은 URL을 통한 데이터 유출 차단. 사용자가 직접 붙여 넣은 URL도 같은 취급인지는 자료에서 확인 못 함.
  - https://openai.com/index/ai-agent-link-safety/ (직접 열람은 403, 2차 자료로 확인: https://www.gend.co/blog/openai-ai-agent-link-safety)
- **이것이 설명하는 것:** 2026-03 Proxy_AIArt에서 "AI가 조립한 URL은 차단, 사용자가 전체 URL을 붙여 넣었을 때만 성공"(3.3)은 우연이 아니라 설계된 규칙이었다. 원칙 5와 절대 URL 규칙의 근거가 공식 문서로 생김.
- **(이후 확인됨 — 같은 날 앱 테스트로 사실로 드러났고 안내판은 "주소를 입력하세요"로 바뀌었다. `docs/test-log.md`)** **안내판 시나리오의 위험 (가장 중요):** 사진에서 읽어 낸 주소는 "사용자 메시지 속 URL"이 아니라 AI가 읽어 낸 글자다. 앱에 따라 거부될 수 있다. 미검증. → 최우선 테스트. 대비: 안내판에 이름을 글자로 같이 적어 검색으로 찾아갈 수 있게(검색 결과의 URL은 허용됨), 주소는 손으로 칠 수 있을 만큼 짧게.
- **색인이 중요해짐:** 새 도메인·새 주소는 색인되기 전까지 경고 대상. → sitemap, 검색엔진 허용, 안내판 인쇄 전에 미리 배포. "오늘" 같은 바뀌는 정보는 날짜별 새 주소가 아니라 고정 주소에서 내용만 교체.
- **캐시:** fetch 결과가 캐시되므로 "오늘의 정보"가 어제 것일 수 있다. → 본문에 날짜를 글자로.
- **손님 행동:** 메뉴판을 찍어 AI에게 번역·추천시키는 전용 앱이 여럿 있을 만큼 "찍어서 AI에게 보내기"는 이미 있는 습관. 다만 규모를 보여 주는 조사 수치는 찾지 못함.
- **못 찾은 것:** 국내 AI 앱(뤼튼·클로바X·에이닷·카나나)의 URL 읽기 동작. 무료 ChatGPT에서 링크 열기가 되는지는 자료가 엇갈림. 둘 다 직접 테스트.
- 비전 모델의 글자 읽기는 대체로 정확하나 읽지 못한 부분을 그럴듯하게 지어내는 경우가 보고됨. URL 한 글자 오독은 곧 실패이므로 짧은 주소·헷갈리는 글자 회피 규칙은 유지.

### 3.3 자체 실험에서 배운 것 (2026-03)

- Proxy_AIArt에서 Claude는 (1) 처음엔 페이지의 GET 지시를 인젝션으로 보고 거부, (2) 제작자 본인 요청 후 시도했으나 AI가 조립한 URL은 시스템이 차단, (3) **사용자가 전체 URL을 직접 붙여넣었을 때만 성공**.
- Gemini는 페르소나는 수용하면서 데이터 전송은 차단.
- 도메인 오타(`proxy-ai-art` vs `proxy-aiart`) 하나로 실패한 적 있음 → URL은 짧고 헷갈리지 않게.
- 결론: "AI가 데이터를 URL에 실어 보내기"는 가장 먼저 막히는 패턴. 원칙 5(AI가 쓰고 사람이 보낸다)의 근거.
